# MA Runtime Module

## Ownership and current scope

- Feature development A owns production files and this module document. Independent Q owns tests and fixtures; feature development must not edit them.
- Batch A1 defines only the six exported data contracts in `contracts.ts`; those types do not validate or authorize values. Batch A2 adds only the standalone execution journal and its structural/association validation.
- `execution-journal.ts` owns a private per-session `execution.jsonl` and `.writer.lock`. Its writer assigns contiguous sequence numbers, accepts at most 256 unfinished appends including the active sync, and synchronizes accepted records before resolving them. A write/sync failure prevents further writes by that instance.
- Complete invalid records are corruption; an unconfirmed final segment is reported separately and prevents opening a writer. Never truncate, skip corrupt complete lines, or clear a crashed writer's lock. `readExecutionJournal` is diagnostic only and does not acquire write authority or repair data.
- A2 does not implement identity issuance, tool/Cloud authorization, Turn gating, Pi history restoration, or owner-death lock recovery. A recorded receipt remains caller-supplied data, not independently verified external evidence.
- R2a adds only ModelCallBinding, ModelCallReceipt, InvocationOrigin and TurnCompletion types, plus model.prepared/model.dispatching/model.receipt/execution.model-bound/turn.completed journal shapes. Required fields must be own enumerable data properties; optional fields are read only when own and valid. Model scope matches the enclosing event, and model receipt callId matches its call. The six earlier event shapes remain readable without rewriting records or inventing an origin.
- requestSha256 means SHA-256 of the UTF-8 bytes of native JSON.stringify applied to the final actual supplier request, without sorting or canonical reordering. R2a validates only the lowercase 64-character hex shape; the later bridge owns request construction and hash computation. AbortSignal, raw requests and responses do not enter these journal records.
- R2a journal acceptance alone does not enforce cross-event model/tool state. R2b below adds the shared TurnGate transitions; retry decisions, recovery and authorization still belong to later integration. A turn.completed record alone is not Mission acceptance or proof of financial settlement.
- A3 adds `turn-gate.ts` for a fresh journal in one process. Its async factory reads the journal before exposing the gate. Existing records or an incomplete tail require recovery; read/write failure pauses the gate. Neither path silently resumes an old Turn.
- One journal object has one gate owner: calls for the same session share initialization and the same gate instance; a conflicting session is rejected with `TURN_INVALID_SCOPE`. Ownership is registered before journal reading, so concurrent factory calls share cancellation state. A newly opened journal object still follows the existing-record recovery requirement.
- `stop` fences the target Turn synchronously, including a pending registration or dispatch fsync. Dispatch attempts already entering the journal remain in-flight even if cancellation prevents returning a permit. A permit proves durable local intent only, not tool authorization, a Cloud budget grant, or remote execution.
- A3 binds subsequent Turns to the first operationId and budgetRef. R2b releases this local binding only after durable normal completion, so a trusted Host may explicitly register another operation/budget with a larger epoch. Stop preserves the original binding; neither path grants or resets Cloud budget authority. Old call/tool identities and receipts retain their original scope permanently within the gate.
- R2b adds prepareModel/markModelDispatching/recordModelReceipt/bindInvocation/recordReceipt/complete to the same shared gate, journal and queue. Every input, including factory options, requires its declared own enumerable data fields; optional fields are copied only when own and valid. Model attempts and tool origins are reserved synchronously; receipts occupy their identity before queueing, and confirmed state changes only after journal synchronization.
- Prepared models may close only with not_sent. Once dispatching starts, not_sent requires evidenceRef; an unknown model/tool receipt can become confirmed only with evidenceRef, and conflicting terminal receipts are rejected. Evidence references remain caller-provided correlation data: the later bridge must establish their truth. Same active-Turn model calls may run concurrently; explicit unknown or unresolved revoked/older-Turn dispatch blocks new model dispatch. A pending unknown receipt remains blocking until a confirmed receipt is durable.
- A new tool dispatch requires a durable binding to a succeeded model receipt and the immutable full Invocation. The tuple (sessionId, epoch, callId, toolCallId) cannot be rebound to another executionId. Confirmed diagnostic failures terminate the tool obligation; stopConfirmed alone cannot clear unknown risk. Late receipts update only their original stored identity and never issue new work.
- complete claims the Turn synchronously only when no prepared model, pending/unconfirmed dispatch or bound tool without a terminal receipt remains. It synchronizes turn.completed before returning a local completion receipt; stop and complete cannot both win. Journal failure pauses the gate, old nonempty logs remain diagnostic recovery_required, and no origin is synthesized for old events. This is not Mission acceptance, Cloud settlement, automatic recovery or a provider/tool permission.
- F1 adds an internal text-only `pi-session.ts` using the real pinned Pi SDK, an explicit borrowed ModelRuntime, empty resources and an in-memory Pi session. Built-in/custom tools, automatic resources, retry, cache warming, compaction and telemetry are disabled. It neither loads the old loop nor grants Host/Cloud authority.
- F1 captures each Turn independently, rejects reused Turn IDs/non-increasing epochs, and holds the prompt slot through SDK preflight and final idle. It does not bind a facade permanently to one operation/budget. Durable authorization and normal Turn completion remain separate later work.
- User cancellation is latched before awaiting SDK abort. A public agent_start listener repeats the abort after preflight creates the SDK run; close waits for the entire prompt and idle before disposal. Late observations retain their original run, observers receive independent snapshots, and unexpected tools fail separately from user cancellation. Local idle/cancel does not prove remote effects stopped or financial settlement.
- Follow the coordinator's frozen batch scope. Later journal, event, permit, and constructor contracts require their own approved implementation node.

## Boundaries for later implementation

- Pi owns model conversation history and its execution loop. This module may own execution correlation and recovery facts, but must not introduce a second transcript or loop.
- Host identity, permissions, current Turn, and Cloud budget authorization must be checked at their trusted boundaries. A TypeScript shape, ID string, hash, or receipt is not proof of authorization.
- Keep model logicalCallId/callId separate from tool toolCallId/executionId. Keep tool serverId and toolName together when correlating receipts.
- Do not persist raw tool arguments, credentials, Host tokens, or resolvable Secure Input references in execution journals or model history. Persist only the approved hashes, scope data, and safe receipt references.
- Future execution dispatch must follow durable intent recording; future receipt confirmation must follow durable receipt storage. A2 supplies durable journal records but does not wire either ordering guarantee into an executor or Pi.
- Unknown execution results must remain unknown until supported by trustworthy evidence. Cancellation, transport disconnect, or process exit alone does not prove remote execution stopped or that effects did not occur.
- Ordinary confirmed diagnostic failures do not become permanent unfinished obligations. An unrelated success must not erase an unknown effect or an unmet required action.
- This module must not claim Mission acceptance, change Cloud balances, implement Agora internal memory, or silently fall back to the old Agent loop.
